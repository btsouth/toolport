## How launch setup is stored

`args` remains an ordinary literal string array. A bound slot contains the
literal marker `<launch-input>`. The typed `launch.inputs` list declares names,
labels, required status and whether a value is secret; `launch.bindings` says
which slot to replace and which named values and punctuation compose it. Only
nonsecret input values appear in `registry.json`. Secret values live in
Toolport's vault under the server ID and input key. No shell or ambient
environment substitution is used to form an argument. The child process still
receives the final argument through its operating system argv, which may be
visible to local process inspection tools.

Save an incomplete entry, fill its Launch setup and Credentials in the server
editor, then enable it. The enable path refuses missing required inputs, while
Test Connection reports the missing label or vault read problem. Editing the
command or argument list removes the generated binding with an explicit editor
notice. Untouched legacy catalog entries migrate under the registry lock; edited
entries and their arguments stay as they are. Setup exports and team payloads
carry the binding structure and labels but clear all input values. Team members
can fill their own values from the Launch setup button without changing the
team's command. A child failure after bound arguments are resolved is reported
without the child's output, because even a bounded output tail could reveal a
fragment of a value.
